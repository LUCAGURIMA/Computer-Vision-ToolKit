EXPLICAÇÃO DETALHADA DA ARQUITETURA E BASE DO SISTEMA DE INSPEÇÃO POR VISÃO COMPUTACIONAL
================================================================================

Este documento explica, de forma didática, como o sistema de inspeção por visão computacional
foi estruturado. Vamos começar do básico e ir avançando aos conceitos mais complexos.

================================================================================
1. O QUE É ESTE SISTEMA?
================================================================================

Imagine que você precisa inspecionar frutas em uma linha de produção. Em vez de uma pessoa
olhando cada fruta, este sistema usa uma CÂMERA + INTELIGÊNCIA ARTIFICIAL para:

1. Tirar fotos das frutas automaticamente
2. Analisar as imagens com IA (Inteligência Artificial)
3. Detectar defeitos como manchas, impurezas ou óleo
4. Classificar como "BOA" ou "RUIM"
5. Salvar os resultados

O sistema tem duas interfaces:
- Desktop (janela no computador)
- Web (página no navegador)

================================================================================
6. COMO AS PARTES SE COMUNICAM
================================================================================

VAMOS IMAGINAR UM FLUXO COMPLETO:

1. USUÁRIO CLICA "INICIAR INSPEÇÃO" na interface desktop
   ↓
2. MainWindow (interface) chama core.inspect_image()
   ↓
3. SystemCore pede para camera_manager.capture() tirar foto
   ↓
4. CameraManager pede para active_camera.capture() (ex: WebcamCamera)
   ↓
5. WebcamCamera usa OpenCV para tirar foto da webcam
   ↓
6. Foto volta: WebcamCamera → CameraManager → SystemCore
   ↓
7. SystemCore envia foto para segmentation_model (IA detecta defeitos)
   ↓
8. SystemCore envia foto para classification_model (IA classifica BOM/RUIM)
   ↓
9. Resultados voltam para SystemCore
   ↓
10. SystemCore devolve resultados para MainWindow
    ↓
11. MainWindow mostra resultados na tela

CADA CAMADA SÓ CONHECE A CAMADA IMEDIATA ABAIXO!

================================================================================
7. POR QUE MÚLTIPLAS CAMADAS? (ARQUITETURA EM CAMADAS)
================================================================================

IMAGINE UM RESTAURANTE:

🍽️  CAMADA DE APRESENTAÇÃO (Interface)
    - Garçom (MainWindow) - recebe pedidos do cliente
    - Mostra cardápio, anota pedidos, entrega comida

🍳  CAMADA DE NEGÓCIO (SystemCore)
    - Cozinheiro-chefe - coordena tudo
    - Decide quais ingredientes usar, como cozinhar

🏪  CAMADA DE DADOS/ACESSO (CameraManager, ModelManager)
    - Comprador de ingredientes (CameraManager encontra câmeras)
    - Estoque (ModelManager carrega modelos de IA)

VANTAGENS:
1. **Mudanças isoladas**: Posso trocar webcam por Basler sem mudar interface
2. **Reutilização**: Mesmo código de câmera serve para desktop E web
3. **Testes fáceis**: Posso testar câmera separadamente da IA
4. **Manutenção**: Bug na câmera não afeta a IA

8. CONCEITOS AVANÇADOS USADOS
================================================================================

8.1 POLIMORFISMO - "MESMA AÇÃO, DIFERENTES RESULTADOS"
-------------------------------------------------------

# Todas as câmeras sabem fazer isso:
camera.initialize()  # Mesmo método

# Mas cada uma faz de um jeito:
webcam.initialize()    # Abre webcam do computador
basler.initialize()    # Conecta câmera industrial
mock.initialize()      # Cria imagem fake para testes

8.2 DEPENDENCY INJECTION - "PASSAR FERRAMENTAS DE FORA"
-------------------------------------------------------

# Em vez de criar dentro da classe:
class MainWindow:
    def __init__(self):
        self.core = SystemCore()  # Criado aqui dentro

# Passamos de fora (mais flexível):
class MainWindow:
    def __init__(self, core: SystemCore):
        self.core = core  # Recebido de fora

VANTAGEM: Podemos passar um SystemCore falso para testes!

8.3 SINGLETON PATTERN - "APENAS UMA INSTÂNCIA"
-----------------------------------------------

class ModelManager:
    _instances = {}

    @classmethod
    def get_instance(cls, model_type):
        if model_type not in cls._instances:
            cls._instances[model_type] = ModelManager(model_type)
        return cls._instances[model_type]

# Garante que só existe um ModelManager para "segmentation"
# Economiza memória e evita conflitos

9. POR QUE PYQT5 PARA INTERFACE DESKTOP?
================================================================================

PyQt5 é uma biblioteca para criar interfaces gráficas em Python.

ALTERNATIVAS CONSIDERADAS:
- Tkinter: Muito básica, feia
- PySide: Similar ao PyQt, mas menos madura
- Kivy: Mais para mobile
- Dear PyGui: Muito nova

PyQt5 FOI ESCOLHIDO PORQUE:
- Interface profissional e moderna
- Muitos componentes prontos (botões, listas, etc.)
- Boa documentação
- Suporte a threads (importante para câmera + IA)

================================================================================
10. POR QUE ULTRALYTICS/YOLO PARA IA?
================================================================================

YOLO (You Only Look Once) é um tipo de rede neural para detectar objetos em imagens.

POR QUE YOLO?
- Muito rápido (processa imagens em tempo real)
- Detecta múltiplos objetos de uma vez
- Fácil de usar com Python
- Modelos pré-treinados disponíveis

COMO FUNCIONA NO SISTEMA:
1. Modelo de SEGMENTAÇÃO: encontra manchas, impurezas, óleo na fruta
2. Modelo de CLASSIFICAÇÃO: decide se fruta é "BOA" ou "RUIM"

11. SISTEMA DE LOGGING - POR QUE TUDO É GRAVADO?
================================================================================

O sistema grava tudo que acontece em arquivos de log.

2026-02-04 14:30:14 | INFO | 🚀 Inicializando SystemCore...
2026-02-04 14:30:14 | INFO | 📷 Inicializando câmera...

POR QUE LOGS?
1. **Debug**: Quando algo dá errado, vemos o que aconteceu
2. **Monitoramento**: Acompanhar performance
3. **Auditoria**: Provar que inspeções foram feitas corretamente

NÍVEIS DE LOG:
- DEBUG: Detalhes técnicos (para programadores)
- INFO: Eventos normais
- WARNING: Avisos (não erros, mas atenção)
- ERROR: Erros que impedem funcionamento
- CRITICAL: Erros graves

14. CONCLUSÃO - POR QUE ESTA ARQUITETURA FUNCIONA BEM
================================================================================

Este sistema foi construído seguindo PRINCÍPIOS SÓLIDOS de engenharia de software:

1. **S**ingle Responsibility: Cada classe faz uma coisa só
2. **O**pen/Closed: Fácil adicionar novas câmeras/modelos
3. **L**iskov Substitution: Qualquer ICamera funciona no lugar de outra
4. **I**nterface Segregation: Interfaces pequenas e específicas
5. **D**ependency Inversion: Depende de abstrações, não implementações

RESULTADO:
- ✅ Código organizado e fácil de entender
- ✅ Fácil adicionar novas funcionalidades
- ✅ Fácil testar e debugar
- ✅ Robusto e confiável
- ✅ Manutenível a longo prazo

Esta arquitetura permite que o sistema cresça: adicionar novas câmeras,
novos tipos de IA, novas interfaces, sem grandes retrabalhos.
